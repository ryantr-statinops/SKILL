# Project scoping

## When to use
Use before committing to a new personal project or major feature.

## When not to use
Do not use for a small, already-scoped maintenance change.

## Personal principles
Prefer a clear useful outcome, small first boundary, and evidence over feature volume.

## Workflow
1. Define user/problem and desired outcome.
2. Identify constraints, non-goals, dependencies, and risks.
3. Define a thin success path and acceptance criteria.
4. Separate MVP from later exploration.

## Decision rules
Choose the smallest scope that can test the central assumption.

## Constraints
Do not turn unknowns into commitments without evidence.

## Failure modes
If the problem or user is unclear, pause scope expansion and clarify it.

## Expected output
Produce a problem statement, scope, non-goals, MVP, risks, and success criteria.

## Validation
Another person can explain what will and will not be built from the scope alone.
